# 第 07 章：自己写出“复用和清理”

[上一章](/game/rust/bevy-immediate/attach) · [目录](/game/rust/bevy-immediate/main) · [下一章：接入 Bevy](/game/rust/bevy-immediate/mini-bevy)

## 本章目标

先离开窗口和 Bevy，用几十行标准库代码实现核心思路。这样再读项目源码时，就能把框架细节与算法分开。

完整源码：[lesson07_mini_core.rs](/game/rust/bevy-immediate/examples/lesson07-mini-core)。

它是控制台教学模型：数字代表实体，字符串路径代表 ID。它不创建 Bevy 实体、不布局、不画图，也不实现事件系统。路径用我们手写的固定字符串，不是通用的路径编码方案。

## 1. 先说需求

我们想每轮写：

```rust
ui.begin_frame();
ui.node("root/title");
if show_help {
    ui.node("root/help");
}
ui.end_frame();
```

并得到三个行为：第一次遇到 ID 时分配实体；再次遇到时找回实体；这一轮没遇到的旧 ID 被删除。

## 2. 三份数据就能开始

```rust
#[derive(Default)]
struct MiniUi {
    next_entity: u64,
    entities: HashMap<String, u64>,
    visited: HashSet<String>,
}
```

- `next_entity` 像取号机，给新实体分配数字。
- `HashMap` 是按键查值的字典，这里保存 ID 到实体编号的关系。
- `HashSet` 只保存是否出现过，这里记录本轮访问过的 ID。

例如 entities 可以保存 `"root/title" → 0`，visited 可以保存本轮出现的 `"root/title"`。

## 3. 开始一轮：清空本轮签到表

```rust
fn begin_frame(&mut self) {
    self.visited.clear();
}
```

注意清空的是 visited，不是 entities。上轮创建的实体仍留在字典里，等着这一轮复用。

## 4. 描述一个节点：先查，再创建

核心片段：

```rust
assert!(self.visited.insert(path.to_owned()), "duplicate id in one frame: {path}");
if let Some(&entity) = self.entities.get(path) {
    return entity;
}
let entity = self.next_entity;
self.next_entity += 1;
self.entities.insert(path.to_owned(), entity);
entity
```

`to_owned()` 从借用字符串创建拥有内容的 String，以便存入集合。

`HashSet::insert` 在这个值之前不在集合时返回 true。因此第一句既签到，也拒绝同一轮重复的 ID。`assert!` 在条件为 false 时让程序报错；真实库的碰撞处理不同，本模型用直接报错帮助学习。

`entities.get(path)` 返回 `Option<&u64>`；`Some(&entity)` 匹配并复制出数字。这里 u64 可以轻量复制。

最后一行没有分号，所以新编号成为返回值。

## 5. 结束一轮：删除没签到的条目

完整程序会先收集没有出现在 visited 中的键，再逐个删除，并打印日志。

为什么不在遍历字典时立刻删除？因为正在遍历字典时又修改它的结构，会产生借用冲突。与上一章列表删除一样，先收集再修改使步骤清楚。

程序还对删除列表排序，只是为了让教学输出稳定，与算法是否能复用无关。

## 6. 运行并逐行对照

可以跳过全部图形依赖，直接运行：

```bash
rustc --edition=2024 Doc/tutorial/src/bin/lesson07_mini_core.rs -o /tmp/bevy-tutorial-core
/tmp/bevy-tutorial-core
```

或使用 Cargo：

```bash
cargo run --manifest-path Doc/tutorial/Cargo.toml --bin lesson07_mini_core
```

预期输出：

```text
--- frame 1 ---
spawn  root/title -> entity 0
spawn  root/help -> entity 1
--- frame 2 ---
reuse  root/title -> entity 0
reuse  root/help -> entity 1
--- frame 3 ---
reuse  root/title -> entity 0
remove root/help -> entity 1
```

第一轮有 title 和 help，第二轮还是这两个 ID，第三轮没有描述 help。日志把“描述每帧重新执行，但实体编号保持不变”直接显示了出来。

## 7. 对应真实项目

| 教学模型 | 当前项目 |
|---|---|
| String 路径 ID | `ImmId`，内部保存 u64 哈希 |
| 自增数字 | Bevy `Entity` |
| entities 字典 | `ImmediateModeEntityMapping` |
| visited 集合 | 实体 `ImmMarker.iteration` 与当前轮次 |
| `node()` | `ch_with_manual_id()` 的复用/创建逻辑 |
| 立刻写入字典 | 通过 Commands 创建，观察器维护映射 |
| `end_frame()` | `PostUpdate` 的 upkeep 系统 |

真实项目不用每轮清空一个实体签到集合，而是在节点上写本轮编号。清理时比较编号，就知道谁没有来签到。

## 8. 验证两个关键性质

源码附有两个测试：

1. 调换描述顺序，实体身份保持不变；删除后再次出现，分配新身份。
2. 同一轮重复描述相同 ID，教学模型拒绝它。

无需编译 Bevy 即可执行：

```bash
rustc --edition=2024 --test Doc/tutorial/src/bin/lesson07_mini_core.rs -o /tmp/bevy-tutorial-core-tests
/tmp/bevy-tutorial-core-tests
```

这些测试只证明教学模型的行为；不能把它们当作真实库全部功能正确的证明。

## 练习

把 main 中的第三轮改为第四轮再次出现 help。预期 help 获得新编号，而 title 仍复用编号 0。然后在同一轮连续写两次 `ui.node("root/title")`，阅读重复 ID 报错。
