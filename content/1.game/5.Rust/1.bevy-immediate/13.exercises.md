# 第 10 章：练习、排错与自我检查

[上一章](/game/rust/bevy-immediate/source-map) · [目录](/game/rust/bevy-immediate/main)

## 1. 建议完成的练习

不要同时改所有例子。每次只改一个入口文件，运行确认，再继续。

| 阶段 | 练习 | 验收方式 |
|---|---|---|
| Rust | 修改基础程序的加法函数 | 输出数值符合预期 |
| Bevy | 普通计数器增加 Enter 清零 | 空格增加，Enter 清零 |
| UI 布局 | 修改容器内边距和排列方向 | 能解释画面为何变化 |
| 点击 | 添加不会低于零的 -1 按钮 | 零时继续点击仍为零 |
| 持久状态 | 重启程序 | 资源恢复初始值，理解当前没有磁盘保存 |
| 列表 | 修改标题但保留数据 ID | 内容更新且身份规则不变 |
| attach | 添加第三个独立面板 | 三个计数互不影响 |
| 内核 | 第四轮重新显示 help | help 使用新编号 |
| 能力 | 高亮颜色改成绿色 | 空格切换符合新颜色 |

进阶练习：把列表条目数据改为 `{ id, title, completed }`，点击切换 completed，用不同文字表示状态。先别删除条目，避免同时处理两套行为。需要删除时，再添加独立删除按钮，并保证它有明确的不同 ID。

## 2. 常见报错与现象

### 找不到 `.text()` 或 `.clicked()` 方法

先检查导入：

```rust
use bevy_immediate::ui::{text::ImmUiText, clicked::ImmUiClicked};
```

如果 trait 已导入，再看错误里是不是能力集合不满足 `ImplCap<...>`。自定义集合需要包含对应能力。

### 提示插件没有正确添加或缺少内部资源

使用 `ImmCtx<CapsUi>` 时，要有 `BevyImmediatePlugin::<CapsUi>` 或对应 attach 插件。使用 TutorialCaps 就应注册 TutorialCaps，不能只注册另一套能力集合。

### 空窗口，没有文字

依次检查：

1. 是否运行了想要的 `--bin`。
2. Startup 是否创建了 Camera2d。
3. draw_ui 是否注册到 Update。
4. UI 渲染和默认字体功能是否启用。
5. 容器尺寸、位置和颜色是否让内容可见。
6. 终端有没有启动失败或资源缺失的错误。

创建数据、布局、渲染是不同步骤。窗口出现只证明窗口部分启动，不代表所有内容都已正确生成。

### 按钮没有效果

检查公共 button 组件是否完整保留，当前 Cargo 配置是否保留 `ui_picking`，以及是否真正调用了 `.clicked()`。节点上的点击追踪是按需初始化的。

如果修改了布局，还要检查是否有其他覆盖整屏的可拾取节点挡住按钮。不要只因为按钮背景没有变色就判断它没响应；本教程按钮未实现悬停变色。

### 计数总是回到零

检查是否在 draw_ui 里写了 `let mut count = 0`，或每帧把资源字段重新赋值为零。持久值放在 Resource 或需要的 Component 中，并且只在合适时机初始化。

### 列表删除或排序后状态串了

检查 ID 是否来自下标、`.ch()` 自动编号，或者多个同级节点使用了同一个 ID。动态列表使用业务稳定 ID，标题文字不要顺手充当可随时修改的身份。

### 改了 `.on_spawn_insert()`，运行中的旧节点没变

这是初始化接口，仅新建时使用。重启会重新创建；运行期动态属性则应使用对应更新方法或自己写同步逻辑。

### `cannot borrow ... as mutable` 等借用错误

重点找“第一次借用”与“第二次借用”的位置。不要只看最后一行。

遍历 `&state.items` 时，不要在循环内部直接 remove。先记录 ID，循环后 retain。另一个常见情况是仍持有一个节点的借用，又想通过同一上下文开始冲突的操作；尽量让节点变量在最后一次使用后结束，必要时用小花括号划分范围。

### 依赖下载失败、系统库缺失或版本不符

这些与 Rust 语法错误分开处理。确认工具链版本、网络、磁盘和报错中具体系统依赖。不要为了绕过一个系统库错误，随意把 Bevy 改成其他大版本；本教程与本地库使用同一版本。

### 中文显示成方框

默认字体不保证包含中文字形。先使用教程英文验证逻辑；需要中文时加载支持中文的字体并设置 TextFont 的字体句柄。

## 3. 查错的固定步骤

1. 记下运行的完整命令。
2. 从第一条真正的错误开始读，分清是编译错误还是运行错误。
3. 只改与错误直接相关的一处，再重新检查。
4. 对照对应章节完整源码，确认没有漏掉插件、资源或 trait 导入。
5. 保留一个能运行的版本，再做实验。

编译器长篇输出里，类型名可能很长。先找错误类别，例如“没有方法”“借用冲突”“缺少 trait 实现”，比逐字读完所有泛型更有效。

## 4. 小词典

| 词 | 本教程中的直观含义 |
|---|---|
| World | 保存实体、组件、资源的运行世界 |
| Entity | 一个对象的身份编号 |
| Component | 附在实体上的某种数据 |
| Resource | 按类型获取的共享数据 |
| System | 由引擎调度的数据处理函数 |
| Schedule | 某一阶段如何运行系统的安排 |
| Plugin | 安装资源、系统和配置的组合入口 |
| Query | 按组件条件访问实体数据 |
| Commands | 排队进行实体结构等修改的工具 |
| Bundle | 可以一次插入的组件组合 |
| trait | 类型需要实现的行为约定 |
| 泛型 | 以类型参数复用一份实现 |
| 闭包 | 可传递、可捕获外部变量的小函数 |
| 生命周期 | 编译器用于约束借用有效期的关系 |
| ID | 用于跨次构建识别同一节点的标识 |
| capability | 库中一组扩展行为和访问声明 |

## 5. 不看答案，解释这些问题

1. 普通局部变量为什么不能自动跨帧保存计数？
2. 为什么构建函数每帧执行，窗口里却不会无限增加文字？
3. `.on_spawn_text("A")` 与 `.text(current_value)` 在更新行为上有什么区别？
4. 为什么两个不同面板下面的子节点都可以叫 `"caption"`？
5. 为什么循环中的同一个 `.tch()` 位置还需要每轮额外区分？
6. 删除列表数据后，界面实体为什么可能在后续构建才消失？
7. 一个能力为什么既要有方法实现，也要登记数据访问？

### 参考答案

1. 每次调用函数都会重新执行局部变量的初始化；资源和组件由 World 保存。
2. 稳定 ID 对应已有实体，找得到就复用，缺少时才创建。
3. 前者只在节点新建时设置，后者持续比较并同步内容。
4. 父级范围也参与生成最终 ID。
5. 循环每轮的源码位置相同；需要数据 ID 或作用域前缀。
6. 当前调用可能已经描述过该节点，下一轮不再描述时清理才能识别它已消失。
7. trait 方法定义 API 和实现，访问登记则为能力查询与 ECS 调度提供权限信息。

如果这些问题能用自己的话回答，就可以回到第 09 章沿着真实调用链阅读，而不用同时记住所有文件。
