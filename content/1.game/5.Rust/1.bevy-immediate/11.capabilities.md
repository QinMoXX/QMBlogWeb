# 第 08 章：给界面增加 `.highlighted()` 方法

[上一章](/game/rust/bevy-immediate/mini-bevy) · [目录](/game/rust/bevy-immediate/main) · [下一章](/game/rust/bevy-immediate/source-map)

## 本章目标

理解 trait、泛型与能力集合在这个项目里各做什么，并完成一个真正可运行的扩展。

完整源码：[lesson08_capability.rs](/game/rust/bevy-immediate/examples/lesson08-capability)。运行：

```bash
cargo run --manifest-path Doc/tutorial/Cargo.toml --bin lesson08_capability
```

预期：窗口显示提示和一段带背景的文字；按空格，文字背景在两种颜色之间切换。

这章比前面抽象。可以先照着运行，再分别解释下面四步，不必一次读懂宏展开和底层 unsafe 实现。

## 1. 先确定想要的使用方式

```rust
ui.ch_id("label")
    .text("A custom capability")
    .highlighted(state.0);
```

state 是 `HighlightState(bool)` 资源。它是元组结构体，所以第一个字段用 `.0` 访问。

我们希望 true 时用橙色背景，false 时用深色背景。业务函数不应该每次都重复颜色比较和组件插入逻辑。

## 2. 声明能力需要哪些访问权限

```rust
pub struct CapabilityHighlight;

impl ImmCapability for CapabilityHighlight {
    fn build<Caps: CapSet>(app: &mut App, requests: &mut ImmCapAccessRequests<Caps>) {
        requests.request_component_write::<BackgroundColor>(app.world_mut());
    }
}
```

CapabilityHighlight 是一个用来代表能力的类型，本身不保存每个节点的背景。

`build<Caps: CapSet>` 是泛型函数，表示它可以为不同能力集合初始化，但这个 Caps 必须满足 CapSet 约定。

`request_component_write` 告诉库：“我的方法需要通过能力查询修改 BackgroundColor。”库会据此配置查询访问权限。单纯给 trait 增加一个名字，不会自动获得任意组件的读写权限。

这里的 `app.world_mut()` 在插件初始化阶段使用，和运行时给每个构建函数传入一个全局 `&mut World` 是不同的路径。

## 3. 定义方法，并限制谁可以用

```rust
trait ImmHighlight {
    fn highlighted(self, enabled: bool) -> Self;
}

impl<Caps: ImplCap<CapabilityHighlight>> ImmHighlight for ImmEntity<'_, '_, '_, Caps> {
    // 方法体见下面及完整源码
}
```

这段声明分两层：trait 约定方法签名，impl 提供实现。

`Caps: ImplCap<CapabilityHighlight>` 可以读成：“Caps 里确实包含高亮能力”。只有满足这个要求的 ImmEntity 才得到这份扩展实现。

`self` 按值接收当前构建把手，`-> Self` 把同类型的把手交回去，因此能继续链式调用。`mut self` 允许方法在内部修改它。

三个 `'_` 是让编译器推导当前借用的生命周期，能力集合的类型参数仍然是 Caps。

## 4. 实现：已有组件就改，没有就排队插入

核心片段：

```rust
if let Ok(Some(mut current)) = self.cap_get_component_mut::<BackgroundColor>() {
    if current.0 != desired {
        current.0 = desired;
    }
    return self;
}
self.entity_commands().insert(BackgroundColor(desired));
self
```

`desired` 在前面根据 enabled 算出。

返回类型有两层，所以匹配写成 `Ok(Some(...))`：

- `Result` 表示实体查询是否成功。
- `Option` 表示实体上是否存在这个组件。

新实体可能还没经过 Commands 应用，也可能原来就没有 BackgroundColor。两者都需要补充插入路径。

已有组件内容相同时不写入，减少无意义的变化。这里没有使用 `unwrap()` 假设一切已经存在。

对第一次描述且命令还没应用的同一个节点，不要期待连续调用几个相互依赖的读写扩展都能马上读取前一个扩展排队插入的数据；本课只为每个节点描述一次高亮状态。

## 5. 把能力组成一个集合

```rust
pub struct TutorialCaps;
impl_capability_set!(
    TutorialCaps,
    ImplTutorialCaps > ImplCapsEmpty,
    (CapabilityUiBase, CapabilityUiLayoutOrder, CapabilityUiText, CapabilityHighlight)
);
```

当前项目的这个宏使用 `>` 表示需要检查的能力子集关系，不是 Rust 继承语法。这里检查集合满足空能力集合，便于从最小组合开始。

这组能力包含：

| 能力 | 本课用途 |
|---|---|
| `CapabilityUiBase` | 为维护系统配置相对于 Bevy UI 的顺序 |
| `CapabilityUiLayoutOrder` | 跟踪并整理子节点排列顺序 |
| `CapabilityUiText` | 提供 `.text()` 所需的访问 |
| `CapabilityHighlight` | 提供我们自己的背景写入能力 |

之后 main 改用 `BevyImmediatePlugin::<TutorialCaps>::new()`，构建参数改为 `ImmCtx<TutorialCaps>`。插件类型与系统使用的集合必须一致。

本课没用点击，所以集合里没有点击能力，使用空格输入资源切换状态。键盘资源由普通系统参数读取，没有通过高亮能力访问。

## 6. 为什么这有助于理解 Rust

在这个具体例子里：

- trait 定义“有什么方法”。
- impl 定义“方法怎样工作”。
- 泛型让方法适用于不同能力组合。
- trait bound 限制“哪些组合可以调用”。
- 初始化时的访问请求告诉 ECS“运行时要访问什么”。

编译期约束和运行期访问登记各有用途。实现扩展时两部分都要写对。
