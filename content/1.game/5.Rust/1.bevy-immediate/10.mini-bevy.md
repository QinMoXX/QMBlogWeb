# 第 07B 章：不用本库，自己把简化内核接入 Bevy

[上一章](/game/rust/bevy-immediate/mini-core) · [目录](/game/rust/bevy-immediate/main) · [下一章](/game/rust/bevy-immediate/capabilities)

## 本章目标

把上一章的数字换成真正的 Entity，把手动分帧换成 Bevy 调度，做出自己的最小即时界面插件。这章展示的是库内核的搭建过程，接着第 08 章再回到真实库的扩展方式。

完整源码：[lesson07b_mini_bevy.rs](/game/rust/bevy-immediate/examples/lesson07b-mini-bevy)。它使用 Bevy 和公共外观函数，但没有调用 bevy_immediate 的 API。

```bash
cargo run --manifest-path Doc/tutorial/Cargo.toml --bin lesson07b_mini_bevy
```

预期：窗口显示一行提示，空格控制第二行显示和隐藏；终端会在创建、删除时打印实体身份，正常复用不会反复打印 spawn。

## 1. 把内存放进 Resource

```rust
#[derive(Resource, Default)]
struct MiniMemory {
    nodes: HashMap<String, Entity>,
    visited: HashSet<String>,
}
```

与上一章相比只有实体值变成 Bevy Entity，并增加 Resource 派生。这样数据可以保存在 World，系统通过 ResMut 获取。

## 2. 自己写一个 Plugin

```rust
struct MiniImmediatePlugin;

impl Plugin for MiniImmediatePlugin {
    fn build(&self, app: &mut App) {
        app.init_resource::<MiniMemory>()
            .add_systems(First, begin_frame)
            .add_systems(PostUpdate, cleanup.before(bevy::ui::UiSystems::Prepare));
    }
}
```

这就是插件的实质：一个按框架约定实现 build 的类型，用来登记资源和系统。它不需要是什么神秘的大型对象。

安排如下：

```text
First：清空 visited
Update：draw 根据业务数据描述节点
PostUpdate：删除没出现的节点，安排在 UI Prepare 前
```

First 不能清空 nodes，否则每帧都会失去可复用实体的映射。

## 3. 把 node 换成真正的创建命令

node 方法接收 ID、父实体、Commands 和用于检查实体是否存在的 Query。返回 `(Entity, bool)`，第二个值表示是否新建。

核心查找片段：

```rust
if let Some(&entity) = self.nodes.get(id)
    && existing.contains(entity)
{
    return (entity, false);
}
```

这里的 `if let ... && ...` 同时要求字典有记录、World 里的实体仍有效。仅保存了编号，不代表实体一定还活着，可能有其他系统把它删除了。

创建片段：

```rust
let mut new_entity = commands.spawn_empty();
if let Some(parent) = parent {
    new_entity.insert(ChildOf(parent));
}
let entity = new_entity.id();
self.nodes.insert(id.to_owned(), entity);
(entity, true)
```

`spawn_empty()` 排队创建实体，先取得保留的 Entity；组件真正进入 World 仍要等命令应用。ChildOf 指向父实体，构成层级。

这个模型直接把身份存进 ResMut 字典。真实库通过观察器维护映射，从而采用不同的资源访问组织。不要把模型的这一小段照搬成“真实实现就是直接写映射”。

## 4. 把布局初始化和身份管理分开

draw 中这样使用：

```rust
let (root, is_new) = memory.node("panel", None, &mut commands, &existing);
if is_new {
    commands.entity(root).insert(panel());
}
```

第一步只决定“哪个实体”；第二步才决定“新实体应该有什么组件”。这个 is_new 分支就是 `.on_spawn_insert(...)` 所包装的核心判断。

子节点传入 `Some(root)`，于是文字挂在面板下面。这里手写完整 ID，例如 `panel/title`，尚未自动组合父级哈希。

## 5. 删除仍然是先收集、再修改

cleanup 找到 nodes 中没出现在 visited 的键，删除映射，再用 `try_despawn()` 排队删除实体。try 版本能容忍相关实体已经随祖先一起被删除等情况。

运行时多次按空格，观察 help 的 Entity：隐藏后再次显示，会得到新的身份；持续存在的 title 不会每帧重建。

## 6. 与真实库相比还缺什么

这个版本只服务于一份明确的 Update 构建流程，父级在节点存续期间保持不变，ID 是手写的全局字符串。它没有实现：

- 自动组合父级 ID 与局部 ID。
- `.add()` 的作用域切换。
- 持续同步任意组件与哈希变化检测。
- 点击追踪与能力查询。
- 描述顺序改变后的 Children 重排。
- 外部修改后的父级修复、不同能力集合隔离和完整调度整合。

例如把同一个已存在 ID 改挂到其他父级，这个模型不会主动修复父级；真实库会检查 ChildOf。把列表顺序改了，这个模型也不会自动整理原有 Children 排列。

先认识这些边界，才能理解真实库为什么需要更多模块。

## 练习

在 draw 中增加一个固定存在的第三行，先取得 node 再在 is_new 时插入 Text。应只在启动时打印它的 spawn。

然后让第三行也受另一个 bool 控制。你已经在不用本库 API 的情况下，完成了一套最小“描述 → 复用 → 清理”的 Bevy 实现。
