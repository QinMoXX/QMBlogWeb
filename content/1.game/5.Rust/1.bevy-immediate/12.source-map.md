# 第 09 章：带着问题读真实项目源码

[上一章](/game/rust/bevy-immediate/capabilities) · [目录](/game/rust/bevy-immediate/main) · [下一章](/game/rust/bevy-immediate/exercises)

## 本章目标

从已经运行过的例子出发，理解真实源码中的一条完整路径。不要从第一行开始顺序读完整个仓库。

## 1. 先把层次摆好

```text
src/lib.rs                           对外导出功能
crates/bevy_immediate_attach/         找挂载点、调用 construct
crates/bevy_immediate_core/           管实体身份、复用、清理、能力访问
crates/bevy_immediate_ui/             文字、点击、选中等具体能力
crates/bevy_immediate_floating_ui/    浮动窗口和锚定等配套功能
examples/                            演示如何组合使用
```

这些 crate 可以理解成同一工程里的多个库包。根库把它们组织成更方便使用的公开接口。

## 2. 问题一：插件启动时准备什么

读 [BevyImmediatePlugin 的 build](/game/rust/bevy-immediate/sources/crates-bevy-immediate-core-src-immediate-mod-rs)。搜索 `fn build`，再找到这个插件的实现。

主要工作依次是：

1. 初始化 ID 映射资源和观察器。
2. 初始化轮次和清理系统。
3. 初始化哈希缓存。
4. 调用能力集合的 initialize，收集读写请求。
5. 保存请求，供后面的 SystemParam 初始化使用。
6. 如果启用了 hotpatching，再初始化热补丁相关逻辑。

把它当作开店前准备货架、账本和规则。它没有在这里把你的业务界面一口气创建出来。

## 3. 问题二：谁调用 construct

读 [attach/src/lib.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-attach-src-lib-rs)，按符号查找：

```text
BevyImmediateAttachPlugin::build
  → 注册 Update 系统 run_system_each_frame
  → 查询带 RootComponent 的实体
  → build_immediate_from
  → RootComponent::construct
```

还有一条根组件添加事件路径：

```text
添加 RootComponent
  → on_insert（实际监听 lifecycle::Add）
  → commands.run_system_cached_with(...)
  → run_system_on_insert
  → RootComponent::construct
```

这条路径用于减少新挂载界面等待到后续常规更新的延迟。它也意味着 construct 不应被当成严格“每帧只执行一次”的业务时钟；保持业务逻辑与构建逻辑的职责清楚。

## 4. 问题三：上下文保存了什么

读 [ctx.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-core-src-immediate-ctx-rs) 和 [immediate/mod.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-core-src-immediate-mod-rs)。

| 结构 | 你已经用过的含义 |
|---|---|
| `ImmCtx` | Bevy 系统提供的工具包 |
| `Imm` | 工具包 + 当前构建范围 |
| `Current` | 当前 ID、父实体、自动编号和前缀 |
| `ImmEntity` | 借用 Imm，保存某个节点的身份和本次临时数据 |
| `ImmScopeGuard` | 临时切换范围，退出时恢复 |

读 `.add()` 时继续找到 `add_child_entities_scope`，再找 `ImmScopeGuard::drop`。看到“保存旧 Current、切换新 Current、退出时恢复”，就理解了嵌套闭包为什么能正确回到外层。

## 5. 问题四：`.ch_id()` 怎么找回实体

按这个顺序读：

1. `.ch_id()`：把传入的数据变成层级 ID 构建请求。
2. [id.rs 的 resolve](/game/rust/bevy-immediate/sources/crates-bevy-immediate-core-src-immediate-id-rs)：结合当前父级与前缀。
3. `ch_with_manual_id()`：在映射里寻找 ID。
4. 如果实体有效，更新 `tracker.iteration`。
5. 检查真实父实体是否变化，需要时排队修改 `ChildOf`。
6. 找不到有效实体时，通过 Commands 创建带 `ImmMarker` 的实体。
7. 调用已注册的节点描述回调，然后返回 ImmEntity。

真实 ID 使用固定种子的哈希，把输入映射成 u64。它用于内存中的身份追踪，不应当作需要跨不同版本长期保存的业务编号格式。哈希也不等于数学上完全不会碰撞。

再读 [entity_mapping.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-core-src-immediate-entity-mapping-rs)：映射由 ImmMarker 的添加、移除观察器维护。新实体创建路径没有直接把新值写入映射资源，而是依赖命令应用后的组件生命周期事件。

## 6. 问题五：清理什么时候发生

读 [upkeep.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-core-src-immediate-upkeep-rs)：

```text
Update 构建：把访问到的 marker.iteration 写成当前轮次
PostUpdate 清理：不同轮次的节点排队 try_despawn
最后：当前轮次加一
```

它管理的是对应 Caps 标记的实体。已有挂载根如果不是由这个即时系统创建并标记，就不是因为 attach 调用本身而被加进这套清理范围。

清理面向这一能力集合的维护轮次，不是每个构建函数各自拥有独立的帧计数。自定义调度时，需要保证构建与清理的相对时机正确；初学阶段沿用教程的 Update 构建即可。

## 7. 问题六：顺序和组件变化怎么处理

读 [layout_order.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-ui-src-layout-order-rs)：每次描述节点时记录它在父级下面的次序，在 PostUpdate 维护 Children 中受管理子节点的排列。这样实体复用和界面重排可以同时成立。

读 [base.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-ui-src-base-rs)：它把库的维护系统集合放在 Bevy UI Prepare 之前。维护集合中的各个系统并没有全部写成严格的从左到右链条，不要把目录中文件顺序当作调度顺序。

读 [text.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-ui-src-text-rs)：`.text()` 比较文字内容再更新。

读 [cached_hash.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-core-src-immediate-cached-hash-rs)：按实体和键保存哈希，支持 `on_hash_change_*`。缓存中已经不存在的实体条目会被维护系统清理。哈希变化检测是可选优化，不是所有组件更新都自动通过一次统一 diff。

## 8. 问题七：点击和自定义能力在哪里

读 [clicked.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-ui-src-clicked-rs)：

```text
First 清空记录
PointerClick 观察器记录事件
clicked() 查询当前实体的记录
首次缺少 TrackClicked 时排队插入标记
```

观察器何时收到事件取决于输入与调度流程。读源码时以系统注册和实际调用顺序为准，不要仅根据某条注释就认为所有点击统一延迟一整帧。

再读 [capabilities/mod.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-core-src-capabilities-mod-rs) 中的宏，对照第 08 章的 TutorialCaps。

最后才读 [system_param_impl.rs](/game/rust/bevy-immediate/sources/crates-bevy-immediate-core-src-capabilities-system-param-system-param-impl-rs)。这里使用查询构建器，把能力申请的组件和资源读写访问登记给 Bevy。组件查询与资源实体查询通过标记过滤区分。unsafe 部分属于进阶框架实现，不建议初学时直接模仿修改。

访问范围明确可以帮助调度，但不是“所有界面都自动并行”。例如同一 Caps 的上下文共享可写哈希缓存，会影响系统之间的并行机会。项目也仍有清理扫描、缓存维护与子节点排序工作，性能应通过真实场景测量。
